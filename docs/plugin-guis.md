# Plugin GUIs: every plugin shows its own panel in every host that can

Every plugin of this tree answers CLAP's `clap.gui` and declares an LV2 `ui:X11UI`. No plugin has GUI code of its own:
the window is drawn by omx-panel's renderer (`omx_panel_window.h`, pugl and NanoVG) from the plugin's panel description
(`omx-panel layout`, omx-panel `docs/panel-layout.md`), and the plugin's two adapters are written once, for all of them.
Governing: omx-plugins#120, descriptions-store spec section 8 (omx-panel `docs/descriptions-store.md`), owner rulings
2026-11-19 (each toolkit draws its own; shared behaviour comes from the C core; no generated MOD GUI in git).

## What each host loads

| Host asks | Gets | Where it lives |
|---|---|---|
| a CLAP host: `get_extension("clap.gui")` | `clap_plugin_gui_t` from the CLAP face | `lib/omx_gui_clap.c`, linked into `lib/omx_clap_face.c`'s table, hand-written once |
| an LV2 host: the plugin's `ui:ui` | a `ui:X11UI` whose `ui:binary` is `<stem>-ui.so` in the bundle | `lib/omx_gui_lv2.c` (hand-written once) plus `generated/<stem>_lv2ui.c`, a stub that names the plugin's layout |
| a host that shows its own panel (plugin-hostd's workers, the console, Zynthian's Tk) | nothing: `clap.gui` is not asked for, the description is read through the store | unchanged |

`clap.gui` is answered for the X11 API, embedded (`CLAP_WINDOW_API_X11`, `set_parent` takes the host's X11 window)
and floating (`set_transient`, `suggest_title`, a window of its own when no parent is given). `get_preferred_api` says X11
and floating, which every Linux host can show. Wayland (`CLAP_WINDOW_API_WAYLAND`, floating only: a Wayland client cannot
embed a foreign surface) waits on the Wayland backend of omx-panel's window (store spec lane 10): the adapter asks the
window for its APIs, so it follows the window and holds no list of its own. Win32 and Cocoa are not offered: this tree
ships for Linux, and the window has no such backend. `set_scale`, `get_size`, `can_resize`, `get_resize_hints`,
`adjust_size`, `set_size`, `show`, `hide` and `destroy` are the CLAP defaults over the window's size, which is the
panel's natural size at the host's scale; `can_resize` is true, since the layout re-flows by width
(`omx_panel_view_visible_columns`).

The LV2 UI is the standard X11UI: `ui:parent` (required) gives the parent window, `ui:portMap` maps a control's symbol to
its port index, `ui:idleInterface` (required) drives events and redraws, `ui:resize` (optional) lets the UI follow the host. The
UI gets values through `port_event` and sends them through the host's `write_function`, as the standard says.

## Where the drawing lives, and why not in the plugin

The drawing, the layout, the gestures and the binding of a control to a value are omx-panel's C core
(`libomx-panel-ui`, below): none is re-implemented here. This repository holds two thin adapters that translate a
host's protocol (CLAP's gui calls, LV2's UI calls) into that library's calls.

The adapters load the library with `dlopen("libomx-panel-ui.so.0")` the first time a host asks to create a GUI, not at
link time. A plugin's DSP binary therefore imports no X11, OpenGL or pugl, loads in plugin-hostd's workers exactly as it
does today (`tools/resource-hints.mjs`' import check holds), and costs nothing to a host that never opens a window. When the
library is not installed, `is_api_supported` answers false and `create` refuses by name: the host shows its own
panel (the CLAP spec's own way to say "no GUI"). That is the absence of an optional package, not a second mechanism.
`omx-plugins-clap` and `omx-plugins-lv2` `Recommends: omx-panel-ui >= <first release that ships it>`: a floor, no ceiling.

## What is generated and what is hand-written

| Piece | Kind |
|---|---|
| each plugin's **layout** (the `omx-panel layout` JSON of its descriptor and declared panel) | generated by `tools/gen.mjs` into `generated/<stem>_params.h` as `OMX_<K>_PANEL_LAYOUT_JSON` (the same call `make panel-layout` already checks), and held fresh by `node tools/gen.mjs --check` |
| `<stem>-ui.so`'s stub, the `ui:X11UI` stanzas of the bundle's TTL | generated by `tools/gen.mjs` from the declaration, never by hand |
| the CLAP `gui` extension, the LV2 UI vtable | hand-written, once, `lib/omx_gui_clap.c`, `lib/omx_gui_lv2.c` |
| the CI gate and its probes | hand-written, `tools/test/plugin-gui-gate.mjs`, `tools/gui-probe.c` |
| **a MOD GUI, a generated LV2 desktop UI bundle** | NOT here: staged key-gated by `omx-plugins-gui` (`omx-panel gui-stage`, #149) and activated by `omx-modgui-sync`; git holds none (`tools/test/no-modgui-check.mjs`) |

The layout is embedded because a plugin must have a GUI with no store, no network and no other package: store spec section
14, decision 4 ("a window with no entry derives the description from its plugin's own and draws it, writing nothing").
When omx-panel's store reader is on main, `libomx-panel-ui` prefers the entry the store holds for the plugin's key (a
user's skin or edit, by `describeFromStored`) and falls back to the embedded layout; the adapters change not at all, because
the library takes the layout as "the plugin's own" and does the choosing.

## The library: who owns it (decision need, default taken)

The generic UI glue is **omx-panel's**: `libomx-panel-ui` (`omx_panel_ui.h`) over its renderer and window. It builds a
view from a layout (or a store entry), binds each control to the host through three callbacks (`set` a value, `read` a
value, `get meter`), owns the window's lifecycle (create embedded or floating, show, hide, size and scale, idle) and
stays free of CLAP and LV2. The store spec already makes the generic LV2 UI library omx-panel's (section 8, lane 10); a second
GUI library in another package would duplicate it. Recommended default, taken here: omx-panel owns it, as one PR in omx-panel
(`Fixes` its issue); this repository carries the adapters only. The alternative is a new package: that costs a repository, a
package pair and a pass, for the same code. No window-toolkit dependency is added: pugl and NanoVG are omx-panel's already
(`docs/renderer.md`, Dependencies).

## The CI gate

Three layers, each held red by a sabotage arm (`tools/test/plugin-gui-gate.mjs --self-test`), run over EVERY plugin of
the tree (`pluginDirs`, so a plugin added by `omx-new-plugin` is covered the moment it exists):

1. **Declared** (fast, no build): the generated bundle TTL of each shipped plugin declares a `ui:X11UI` with a `ui:binary`
   and the plugin's TTL names it with `ui:ui`; the generated CLAP source takes the GUI face and the generated layout
   parses and holds every parameter of the plugin's panel. A new plugin without one is red here. Arm: a tree copy
   with one plugin's stanza removed names that plugin.
2. **Built** (`make test`, probes): `tools/gui-probe.c` loads the built `.clap` and asserts `get_extension("clap.gui")` is
   non-NULL, `is_api_supported(x11, floating)` and `(x11, embedded)` are true when the library is present, `get_size` equals
   the layout's natural size; lilv lists an `ui:X11UI` for the plugin URI whose binary exists and exports
   `lv2ui_descriptor` with the plugin's UI URI. Arm: a face built without the extension fails the probe.
3. **Opens and draws** (a CI job in a container with pugl, NanoVG, Mesa and Xvfb, the way omx-panel's `renderer-window` job
   builds them): under `xvfb-run`, the probe runs CLAP `create`, `set_parent` with a real X11 window, `show`, `set_size`,
   reads the window back (`omx_panel_window_read`) and requires the frame to equal, by omx-panel's own window-versus-buffer
   structure test, the buffer the same layout draws; then the same through the LV2 UI's `instantiate`, `port_event`
   (a value change must change the frame) and `cleanup`. Arm: an empty layout draws a blank frame and is red. Nothing is
   skipped: a missing pugl in the job is a red job, not a skip.

A real host (Carla CLAP and LV2, Ardour via the LV2 adapter, Zynthian VNC) is the owner-facing proof of #120 and runs by
hand; it is listed as not proven until someone runs it.

## Slices, in order, and what waits on what

1. **Design** (this note), own commit.
2. **The gate, red** (omx-plugins): `plugin-gui-gate.mjs` layers 1 and 2 over today's tree, red on every plugin (no GUI),
   with `--self-test`; wired into `make test` and `tools/test/test-split.json`. Waits on nothing.
3. **Generator and adapters, green** (omx-plugins): `gen.mjs` emits the layout, the TTL stanzas and the UI stub;
   `lib/omx_gui_clap.c`, `lib/omx_gui_lv2.c`; the Makefiles build `<stem>-ui.so`; the packages ship it. Layers 1 and 2 go green
   with `libomx-panel-ui` absent (the adapters' absence path), which the built probe states. Waits on nothing.
4. **omx-panel: `libomx-panel-ui`** (omx-panel PR, off `lane/sort-pass-omx-panel`, new worktree `wt/omx-panel-l1-guis`):
   independent of `gui-stage` (#147), which stages files and touches no window; it shares only the window. Waits on the
   window job's pugl and NanoVG packages (already in omx-panel's CI).
5. **Layer 3, the Xvfb end to end** (omx-plugins CI job). Waits on slice 4 released to the channel the job installs from.
6. **Wayland** floating. Waits on omx-panel's window backend (store lane 10).
7. **Store entry preferred over the embedded layout.** Waits on store lanes 1 and 2 (the reader, `describeFromStored`).
8. **`omx-plugins-gui` package** (#149): `gui-stage` over the built bundles. Waits on #147 merged. Its own PR.

The PR closes #120 only when slices 5 and 6 and the hand proofs are in; until then it says `Part of #120` (a `Fixes` on
an unproven issue would close it falsely).

## What is not decided here

No new vocabulary: the layout's words, the window's calls and the extension ids are the ones that exist. No
backward-compatibility mechanism: a plugin whose library is absent offers no GUI, which is a package choice. No generated
toolkit file is committed.
